# siyousho テスト設計

目的: gem の機能（テストの各文の前にスクリーンショットを撮り、HTML の仕様書を生成する）を
テストで担保し、安心してリファクタリングできる状態にする。その上で CI を整備する。

## 1. 現状の実測結果（2026-10-28）

`lib/siyousho.rb` の挙動を、Rails.root と Capybara セッションをスタブした子プロセスと、
ダミー Rails アプリで実測した。

| # | 事象 | 結果 | 影響 |
|---|---|---|---|
| F-1 | 本文が 1 文だけのテスト | `NoMethodError: undefined method 'location' for nil` | テストがエラーになる |
| F-2 | 本文が空のテスト | `NoMethodError: undefined method 'children' for nil` | 同上 |
| F-3 | ソースにアポストロフィ（`"it's"`）を含む | 差し込みコードが `'...'` で囲まれるため `SyntaxError` | 同上 |
| F-4 | ステップに `<` `>` `&` を含む | エスケープされず HTML に出力 | HTML が壊れる |
| F-5 | ブラウザを使わない `ActiveSupport::TestCase` のテストが同じプロセスにある | 全文の前で `save_screenshot` が呼ばれ `rack-test requires a rack application` でエラー | 実アプリでは system test 以外が全滅する |
| F-6 | `require "siyousho"` を Minitest 読み込み前に行う | `NameError`（`Runnable`） | 読み込み順に依存 |
| F-7 | `<meta charset>` がない | 日本語のタイトル・ラベルがブラウザで文字化けし得る | 表示 |
| F-8 | 複数行の文（`do ... end`）のラベル | Unparser による正規化で `{ |i,| ... }` に変形 | 仕様書としての可読性 |
| F-9 | 同名テストが複数クラスにある | 出力ファイル名がメソッド名のみなので上書き | 仕様書の欠落 |
| F-10 | 文間のコメント、日本語テスト名、ローカル変数の引き継ぎ | 期待通り | - |

F-1〜F-4, F-6, F-7 は修正対象の不具合。F-5, F-8, F-9 は仕様の決定が必要（§4）。

## 2. テストの層構成

| 層 | 対象 | 実行形態 | 速度 | 備考 |
|---|---|---|---|---|
| L1 ユニット | HTML 生成、ソース解析と差し込み（純粋関数） | 同一プロセス | 速い | gem を `siyousho/document`, `siyousho/instrumenter`（パッチを当てない）と `siyousho/minitest`（パッチ）に分割し、前者だけを読み込む |
| L2 機能 | Minitest への統合（`run` の差し替え、ライフサイクル、結果集計） | 子プロセスで fixture を実行し、出力と文書を検証 | 1 ケース 0.2 秒程度 | 既存の `test/fixtures/instrumented_run.rb` 方式を汎用ハーネス化。Rails 非依存で `test "..." do` 形式も模倣する |
| L3 E2E | 実 Rails + 実 Chrome | ダミーアプリの system test | 遅い | 最新 Rails × gem がサポートする Ruby。Minitest.after_run で文書を検証（既存） |

方針:
- 期待挙動は「ユーザーから見える出力」（文書の内容・ファイル配置・テスト結果の集計）で書き、
  内部実装（Minitest の内部 API）に依存させない。
- 不具合修正と仕様変更はテストを先に書いてから行う（1 件 = 1 コミット）。

## 3. テスト観点一覧

優先度: P1 = 機能の中核・必須、P2 = 品質・堅牢性、P3 = あれば良い。
状態: OK = 現状満たす、BUG = 要修正、DEC = 仕様決定待ち（§4）、NEW = 追加確認。

## 4. 決定が必要な事項（推奨つき）

| ID | 事項 | 選択肢 | 推奨 |
|---|---|---|---|
| D-1 | 計測の適用範囲（E7） | (a) 全 Minitest テスト（現状） (b) `ActionDispatch::SystemTestCase` には自動適用、それ以外は `include Siyousho::Minitest` でオプトイン (c) 常にオプトイン | (b)。Rails では何もせず動き、実アプリの他のテストを壊さない |
| D-2 | ステップラベル（B1） | (a) Unparser で正規化（現状） (b) 書かれたままのソース | (b)。仕様書として読みやすく、Unparser 依存と Ruby 4.0 の警告もなくなる |
| D-3 | 出力ファイル名（D6） | (a) `tmp/仕様書/<テスト名>.html`（現状） (b) `tmp/仕様書/<クラス名>/<テスト名>.html` と `<クラス名>/<テスト名>/N.png` | (b)。衝突しない。`/` などはサニタイズ |
| D-4 | 撮影失敗時（C3） | (a) テストをエラーにする (b) 画像なしステップとして続行 | (a)。D-1 で適用範囲を絞れば失敗は設定ミスであり、黙って欠けるより良い |
| D-5 | 残骸の掃除（C4） | (a) 放置 (b) テスト開始時にそのテストの出力を削除 | (b) |
| D-6 | skip（E4） | (a) skip までのステップで文書を作る (b) skip したテストは文書を作らない | (b) |
| D-7 | gemspec（F3） | minitest を runtime 依存として `>= 5.25, < 7` を宣言するか | 宣言する。パッチ対象の範囲を利用者に明示できる |
| D-8 | ファイル分割（L1） | `siyousho/document`, `siyousho/instrumenter`, `siyousho/minitest` に分ける | 分ける。ユニットテストの前提 |
| D-9 | RuboCop | 設定を `single_quotes` に変更し自動修正する | 変更する。コードの実態に合わせ、lint ジョブを緑にする |

## 6. 実装順序

1. 決定事項 D-1〜D-9 を確定する。
2. L1 の下地: ファイル分割（D-8）。挙動は変えない。
3. 現状 OK の観点を L1 / L2 で固定する（特性テスト）: A1 A2 A5〜A8, C1 C2, D1〜D3 D5 D7, E1〜E3 E5 E6, F2。
4. 不具合を 1 件ずつテスト先行で修正: A3, A4, A9, B2, D4, F1。
5. 仕様変更をテスト先行で実装: E7 (D-1), B1 (D-2), D6 (D-3), C3 (D-4), C4 (D-5), E4 (D-6), F3 (D-7)。
6. L3 を拡張: G3, G4, G5。CI に package ジョブ追加、lint を緑化（D-9）。
7. 安全網ができた後に `run` の差し替えを `prepend` + `super` に書き直し、状態をインスタンス単位にする（E8）。

## 7. 実装結果（2026-10-28）

決定事項 D-1〜D-9 はすべて推奨案で実装した。§3 の BUG はすべて修正、DEC はすべて決定どおり、NEW は
A10（ヒアドキュメント）、A11（endless def）、A12（読めない／パースできないソースはそのテストのエラー）、
F4（CI の package ジョブ）、G3〜G5 を実装した。E10（Rails のプロセス並列）は未検証。

計画からの差分:
- 旧挙動の特性テスト（§6 の 3）は省いた。承認された仕様変更でラベル・出力先・適用範囲が変わるため、
  新仕様に対するテストを直接書いた。
- 構文解析を parser gem から Prism に切り替えた（Ruby 3.4 以降の文法に対応し、警告も消える）。
  ヒアドキュメントの本文は文の位置情報に含まれないため、Instrumenter が明示的に取り込む。
- `run` の差し替えは `prepend` + `super` 方式で実装し、状態はテストインスタンスに持つ（E8 も解消）。
